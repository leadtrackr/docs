<Warning>
**Preview.** This page describes how attribution data will work once cookie forwarding is live. It is not available in the API yet.
</Warning>

You don't need to know which cookie holds which click ID. Send the visitor's cookies and the URL of the page the lead came from. LeadTrackr reads the click IDs, analytics IDs and consent status it needs and throws everything else away.

## The short version

<Tabs>
  <Tab title="From your server">
    Forward the `Cookie` header of the visitor's request, unchanged, to [Create Server-Side Lead](/api-reference/leads/create-server-side-lead). Add the page URL to `attributionData`.

    ```bash
    curl -X POST https://app.leadtrackr.io/api/leads/createServerSideLead \
      -H "Content-Type: application/json" \
      -H "X-API-Key: your-api-key-here" \
      -H "Cookie: _ga=GA1.1.1234567890.1234567890; _gcl_aw=GCL.1234567890.abc123; _fbp=fb.1.1612345678.9876543210" \
      -d '{
        "projectId": "your-project-id",
        "userData": { "email": "john@example.com" },
        "attributionData": {
          "pageUrl": "https://www.example.com/contact/?gclid=abc123"
        }
      }'
    ```

    This is the most complete option. Server-side tracking cookies such as `FPGCLAW` and `FPID` are `HttpOnly`, so only your server can see them.
  </Tab>
  <Tab title="From the browser">
    A browser can't set a `Cookie` header for another domain. Put `document.cookie` in `attributionData.cookies` and send it to [Create Lead](/api-reference/leads/create-lead).

    ```javascript
    await fetch("https://app.leadtrackr.io/api/leads/createLead", {
      method: "POST",
      headers: { "Content-Type": "application/json" },
      body: JSON.stringify({
        projectId: "your-project-id",
        userData: { email: "john@example.com" },
        attributionData: {
          cookies: document.cookie,
          pageUrl: location.href
        }
      })
    });
    ```

    `HttpOnly` cookies are not in `document.cookie`. If you run server-side tracking, send the lead from your server instead.
  </Tab>
</Tabs>

That is all you need. The fields you may already send today (`gclid`, `fbc`, `cid`, …) keep working, see [Send fields yourself](#send-fields-yourself).

## Your server, step by step

<CodeGroup>
```php PHP
$payload = [
    "projectId" => "your-project-id",
    "userData" => ["email" => $_POST["email"]],
    "attributionData" => [
        "pageUrl" => $_SERVER["HTTP_REFERER"] ?? null,
    ],
];

$ch = curl_init("https://app.leadtrackr.io/api/leads/createServerSideLead");
curl_setopt_array($ch, [
    CURLOPT_RETURNTRANSFER => true,
    CURLOPT_POST => true,
    CURLOPT_HTTPHEADER => [
        "Content-Type: application/json",
        "X-API-Key: your-api-key-here",
        "Cookie: " . ($_SERVER["HTTP_COOKIE"] ?? ""),
    ],
    CURLOPT_POSTFIELDS => json_encode($payload),
]);
curl_exec($ch);
```

```javascript Node.js (Express)
app.post("/contact", async (req, res) => {
  await fetch("https://app.leadtrackr.io/api/leads/createServerSideLead", {
    method: "POST",
    headers: {
      "Content-Type": "application/json",
      "X-API-Key": "your-api-key-here",
      Cookie: req.headers.cookie ?? ""
    },
    body: JSON.stringify({
      projectId: "your-project-id",
      userData: { email: req.body.email },
      attributionData: { pageUrl: req.get("referer") }
    })
  });
  res.sendStatus(204);
});
```

```javascript Next.js (route handler)
export async function POST(request) {
  const form = await request.formData();

  await fetch("https://app.leadtrackr.io/api/leads/createServerSideLead", {
    method: "POST",
    headers: {
      "Content-Type": "application/json",
      "X-API-Key": process.env.LEADTRACKR_API_KEY,
      Cookie: request.headers.get("cookie") ?? ""
    },
    body: JSON.stringify({
      projectId: "your-project-id",
      userData: { email: form.get("email") },
      attributionData: { pageUrl: request.headers.get("referer") }
    })
  });

  return new Response(null, { status: 204 });
}
```
</CodeGroup>

<Tip>
When a form posts to your server, the `Referer` header is usually the page the form was on. If your site sets a strict `Referrer-Policy`, the query string is missing from it. In that case send `location.href` along with the form, for example in a hidden field.
</Tip>

## What LeadTrackr keeps

LeadTrackr reads a fixed list of cookie names and URL parameters. Everything else is dropped in memory, before anything is stored or logged.

| Stored as | Read from (URL parameter → cookies) |
| --- | --- |
| `gclid` | `gclid` → `FPGCLAW` → `_gcl_aw` |
| `gbraid` | `gbraid` → `FPGCLAG` → `_gcl_ag` |
| `wbraid` | `wbraid` → `FPGCLGB` → `_gcl_gb` |
| `dclid` | `dclid` → `FPGCLDC` → `_gcl_dc` |
| `cid` | `FPID` → `_ga` |
| `fbc` | `fbclid` → `_fbc` |
| `fbp` | `_fbp` |
| `msclkid` | `msclkid` → `uet_msclkid` → `_uetmsclkid` |
| `uetvid` | `uet_vid` → `_uetvid` |
| `ttclid` / `ttp` | `ttclid` / `_ttp` |
| `li_fat_id` | `li_fat_id` |
| `scclid` / `scid` | `ScCid` → `_scclid` / `_scid` |
| `rdt_cid` / `rdt_uuid` | `rdt_cid` → `_rdt_cid` / `_rdt_uuid` |
| `epik` | `epik` → `_epik` |
| `twclid` | `twclid` |
| `session_attributes` | `_dm_session_attributes` |
| `conversionPage` | Host and path of `pageUrl`, without the query string |
| `consent` | See [Consent](#consent) |

**Never stored:** the raw cookie string, any cookie not in the table above (login cookies, session IDs, shopping carts, …), and the query string of `pageUrl`. A query string can contain personal data, so only the host and path are kept.

A value longer than 512 characters, or in a format LeadTrackr doesn't recognise, is skipped. It is never cut short: half a click ID looks like real attribution and isn't.

## Which value wins

When the same field can be read from several places, the first valid one wins:

1. The URL parameter in `pageUrl`. It is there even when a pixel is blocked or hasn't written its cookie yet.
2. A field you send yourself, such as `attributionData.gclid`.
3. A server-side tracking cookie (`FPGCLAW`, `FPID`, `uet_msclkid`, …).
4. A browser cookie (`_gcl_aw`, `_ga`, `_uetmsclkid`, …).

If a click ID is in the URL, LeadTrackr uses it even without a cookie. Browser IDs such as `cid` and `fbp` are never generated: an ID the ad platform has never seen cannot be matched. The one exception is `fbc`, which Meta allows to be built from an `fbclid`.

## Consent

LeadTrackr stores the visitor's consent status with the lead, in Google Consent Mode terms (`ad_storage`, `analytics_storage`, `ad_user_data`, `ad_personalization`). It reads it from the first source that has it:

1. `attributionData.consent`, when you send it yourself.
2. The `lt_consent` cookie, written by the LeadTrackr WordPress plugin.
3. The cookie of your consent banner (CMP).

```json
"consent": {
  "ad_storage": "granted",
  "analytics_storage": "granted",
  "ad_user_data": "granted",
  "ad_personalization": "denied"
}
```

### Supported consent banners

| Consent banner | Cookie | Statistics → `analytics_storage` | Marketing → `ad_storage`, `ad_user_data`, `ad_personalization` |
| --- | --- | --- | --- |
| Cookiebot | `CookieConsent` | `statistics` | `marketing` |
| CookieYes | `cookieyes-consent` | `analytics` | `advertisement` |
| Complianz | `cmplz_statistics`, `cmplz_marketing` | `cmplz_statistics` | `cmplz_marketing` |
| CookieScript | `CookieScriptConsent` | `performance` | `targeting` |
| OneTrust | `OptanonConsent` | group `C0002` | group `C0004` |
| Borlabs Cookie | `borlabs-cookie` | `statistics` | `marketing` |
| CookieFirst | `cookiefirst-consent` | `performance` | `advertising` |

If the banner doesn't map a category, LeadTrackr leaves that consent type out. It never guesses `granted`.

By default LeadTrackr detects the banner from the cookies it receives. Under **Settings → Tracking → Consent source** you can pin it to one banner, or switch cookie-based consent off. Pin it when:

- your site switched banners and old cookies are still around;
- your OneTrust setup uses other group IDs than `C0002` and `C0004`. Enter your own IDs there.

<Note>
Some banners, such as Usercentrics, keep consent in the browser's local storage rather than in a cookie. LeadTrackr can't see that. Send `attributionData.consent` yourself, or use the GTM tag, which reads consent from Google Consent Mode directly.
</Note>

## Send fields yourself

If you already read cookies yourself, you can keep sending the parsed values. They are still accepted and, under the rules above, a field you send beats a cookie.

<Expandable title="Accepted attributionData fields">
  <ParamField body="cookies" type="string | object">
    The visitor's cookies: a `Cookie` header string (`"_ga=…; _fbp=…"`) or an object of `{ "cookie name": "raw value" }`. Max 16 KB.
  </ParamField>
  <ParamField body="pageUrl" type="string">
    Full URL of the page the lead came from, including the query string. Only the host and path are stored.
  </ParamField>
  <ParamField body="capturedAt" type="number">
    When the visitor was on the page, in Unix milliseconds. Used as the click time when LeadTrackr builds an `fbc`. Defaults to the moment the lead arrives.
  </ParamField>
  <ParamField body="<cookie name>" type="string">
    A single raw cookie under its own name, for example `"_gcl_aw": "GCL.1234567890.abc123"`.
  </ParamField>
  <ParamField body="gclid, gbraid, wbraid, dclid, cid, sid, fbc, fbp, fbclid, msclkid, ttclid, li_fat_id, …" type="string">
    Parsed values, as in the table under [What LeadTrackr keeps](#what-leadtrackr-keeps).
  </ParamField>
  <ParamField body="consent" type="object">
    Consent status in Google Consent Mode terms. Each key is `"granted"` or `"denied"`.
  </ParamField>
</Expandable>

When the same cookie arrives in more than one way, the most explicit one wins: the `Cookie` header, then `attributionData.cookies`, then a cookie sent under its own name.

<Info>
The `Cookie` header is only read on [Create Server-Side Lead](/api-reference/leads/create-server-side-lead). On [Create Lead](/api-reference/leads/create-lead) the browser would send cookies for `app.leadtrackr.io`, not for your site, so it is ignored there.
</Info>
